What's new vs today

  • /projects/[id]/unlock/compose page goes away. Builders pay → land directly in /chat/:matchId.
  • Inbox concept retired. /inbox page hidden from menus; inbox_messages table left in place but unused (can drop in a follow-up).
  • swipe_interest gets a third source: 'paid_unlock'. Today's enum is ('recommended', 'subscribed') - we add this case so the unlock auto-creates a matched row without faking a swipe.
  • chat_messages gets attachments_json - the same JSON-array-of-URLs pattern used on the inbox attachments fix earlier.
  • Image upload via 📷 in the chat input bar. Same FileGridUploader pattern, opens as a popover above the input. Per-message attachment cap of 6.
  • "Paid unlock" badge on the chat header for the homeowner so they know this builder paid rather than was picked in their deck. Badge hidden on the builder's view.

Server changes

  • unlock-contact.checkout + mock.pay: after writing the active project_contact_unlocks row, also INSERT a swipe_interest row (status='matched', source='paid_unlock'). Returns matchId so the client can route to /chat/:id.
  • chat/messages.post: extend to accept multipart with photos[] (max 6, 10MB each), reuse the close.photos.post.js pipeline (HEIC → JPEG, EXIF strip).
  • chat/messages.get: include attachments on each message in the response.
  • matches list endpoint: surface source so the homeowner-side UI can render the badge.

What I want to confirm before building

  • OK to add 'paid_unlock' to the swipe_interest source enum?
  • "Paid unlock" badge wording / colour OK, or hide entirely?
  • Per-message photo cap of 6 sound right for chat?
  • For now I'd leave the inbox_messages table in place (just stop writing to it) - any in-flight unreplied pitches stay readable. OK to drop in a follow-up?
